# CC-69-A-02 / proposed ADR-022 — conservative publishing intake with visible gaps

**Status: PENDING. Owner risk acceptance is recorded; architecture is NOT approved.**

## CHANGE_CONTROL proposal

- **Change ID/class:** CC-69-A-02; cross-module reliability/correctness, with explicitly proposed operator diagnostic/recovery API additions.
- **Problem/evidence:** At base `1892653`, registry claims M14/M16 consumers and broker retry/dead-letter policy without active delivery. M13 emits PublishFailed only on YouTube processing rejection, invents correlations at emission, and M17 intake/reporting directly read M13 outbox rows. Keyset intake can miss late commits, skip startup history and stall at poison data. Those limitations must be detectable, not hidden by a green notification job.
- **Proposed behavior:** Conservative M17 intake plus strict registered-envelope validation, M13-owned read contracts, persisted origin correlations/final-failure events and bounded OWNER gap inspection/replay. No relay acknowledgement or broker dead-letter guarantee.
- **User/business value:** Honest notification state, observable missing intake receipts, safe bounded correction without repeating publication/provider actions.
- **Affected modules/APIs/schemas/events/prompts/pipelines:** M13 producer/read service, M17 intake/reporting/controller and M19 audit seam; M16 publishing correlation consumer; shared registry metadata; nullable publishing correlation fields. Wire PostPublished@1/PublishFailed@1 remain unchanged. No creative prompt, media generation or vendor change.
- **Cost/security/privacy/policy/reliability impact:** Extra bounded DB reads during explicit diagnostics/replay. OWNER-only, workspace-scoped; return identifiers/status, not raw payload/secrets. Replay may later create in-app notifications under existing fan-out policy; email remains NOT_CONFIGURED pending sender choice. No paid provider or publication call. No automatic retention/history window is invented. Accepted reliability risks remain.
- **Backward compatibility/migration:** Preserve ADR-018 defaults and current wire v1 payloads. New nullable correlation fields do not fabricate historical origins. Additive diagnostic/replay routes; existing notification routes/response shapes remain. No automatic event backfill or cursor reset.
- **Acceptance criteria/tests:** T22-01..12 below, unexecuted.
- **Trade-offs/deferred:** No full relay, active published_at acknowledgement, broker DLQ, automatic poison skip or universal eventual delivery. Manual diagnosis/recovery is bounded but not a guarantee that every loss will be discovered.
- **Owner decision:** A-POL-02 [#6831450311](https://github.com/imTusharsingh/reelforge/issues/69#issuecomment-6831450311) accepts conservative limitations for this remediation only. New endpoint/port/quarantine choices still need Core review; no approval by implication.
- **Core Reviewer decision:** PENDING. [#6831527297](https://github.com/imTusharsingh/reelforge/issues/69#issuecomment-6831527297) requires explicit loss cases, startup/poison behavior, retries/dedupe, operator-detectable gaps, bounded recovery, E6 and independent publication safety.

## ADR-022 proposed decision

### 1. Alternatives

| Property                     | Conservative minimum (recommended under accepted risk)                | Full relay (deferred alternative)                                                        |
| ---------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Intake                       | Existing M17 source keyset and transactional receipt/cursor           | Durable pending-row claim/lease, consumer acceptance/ack                                 |
| Delivery                     | Conditional on observing row within cursor assumptions                | At least once for defined eligible committed rows, with consumer dedup                   |
| Late commit behind watermark | Can be missed; operator scan/replay can detect/repair observed gaps   | Pending scan avoids watermark loss                                                       |
| Fresh cursor                 | No history by default                                                 | Legacy eligibility/backfill must be explicitly decided                                   |
| Retry                        | Unchanged page on next tick after read/validation/transaction failure | Persist attempt counter/next time; existing registry bounds only after explicit approval |
| Poison                       | Source/page blocked, no silent cursor advancement                     | Durable dead-letter state and controlled same-ID requeue                                 |
| published_at                 | NULL; never claims consumer acknowledgement                           | Set after durable acceptance, never before                                               |
| Recovery                     | Bounded explicit source-row scan/replay; repeat scans needed          | Lease recovery, ack retry, dead-letter/requeue tests                                     |
| Scope                        | Read/validation/diagnostics/replay plus existing cursor               | New delivery state/schema/worker and historical eligibility policy                       |

Recommend conservative minimum because owner accepted the scoped risk; Core must explicitly accept its architecture. If reliable eventual delivery of every eligible commit is required now, reject this option and request a separately inventoried full relay. Do not call database dead-letter state a Redis DLQ unless that queue actually exists.

### 2. Exact existing and retained event wire contracts

Strict common envelope:

- eventId UUID; eventType nonempty string; eventVersion positive integer; occurredAt ISO datetime with offset.
- workspaceId UUID; optional channelId UUID; correlationId as existing CorrelationIdSchema; optional causationId UUID.
- idempotencyKey nonempty string; aggregateType nonempty string; aggregateId UUID; strict registered payload.
- PostPublished@1: eventType literal PostPublished, version 1, payload `{ postId: UUID, platform: nonempty string, platformPostId: nonempty string }`.
- PublishFailed@1: eventType literal PublishFailed, version 1, payload `{ postId: UUID, failureCode: nonempty string, retryable: boolean }`.

No wire field/version change is proposed. M13 is the producer. M17 registered publishing intake is the consumer; M17 reports use a separate M13 read service. M14 reads published records through its service; M16 invokes commands and is not an outbox consumer. M11/M15/M16 internal notification sources are not silently converted to registered events.

Registry changes: consumers become only `M17-notifications-and-reporting` for both entries. Add authoritative delivery metadata `{ mode: M17_KEYSET, publishedAtAcknowledgement: false, retry: NEXT_TICK_NO_ATTEMPT_LIMIT, poison: BLOCK_SOURCE, deadLetter: NONE, history: EXPLICIT_BACKFILL_ONLY }`. Existing retryPolicy remains for source compatibility but is explicitly deprecated/declarative, not an executable promise; test no runtime uses it as active delivery. EventRetryPolicy values remain unchanged, not repurposed to claim an implemented broker.

### 3. Exact loss, retry and poison semantics

Retain configured settleMs and source cursor behavior (current defaults: settle 30,000 ms; batch 200; max pages 10; worker tick 30,000 ms; intakeBackfill false). These are existing values, not newly selected retention/SLA policy.

Example missed commit: row timestamp 10:00:00, transaction held open; intake advances to a later tuple while the row is invisible; it commits at 10:01:00 and sorts behind the cursor. Future keyset reads exclude it. A source clock behind the reader's assumed window causes the same loss. A clock ahead can postpone visibility to a later tick. Increasing a settle window reduces some risks but cannot guarantee arbitrary transaction/skew bounds. The existing approximate commit/skew assumptions are not mathematically sufficient to promise zero loss at their extreme combination.

Fresh source at `now - settle` with maximum UUID intentionally excludes historical rows, including same-boundary rows. A restarted source with its existing cursor resumes; deleting/reinitializing a cursor is not an authorized recovery shortcut. `intakeBackfill=true` affects creation of a missing cursor, not a bounded existing-source repair.

Reconstruct complete M13 envelopes from persisted columns with optional fields omitted for nulls. Call parseRegisteredEvent before creating notifications. Require envelope tenant/channel/aggregate to agree with owning M13 rows. A malformed payload, unknown version or inconsistent identity fails the page. No notification insert or cursor advancement for that page. Previously committed pages remain committed. Retrying the next tick uses the same page and dedupe keys. Poison data can block this M13 source indefinitely; the worker continues other sources and reports the source error. No maximum retry/dead-letter success is implied.

Do not silently skip malformed rows or label them delivered. Existing event-specific fan-out and email delivery retries remain separate from outbox intake. Deleted workspaces may be omitted under the existing source behavior; this is not an acknowledgement guarantee for the deleted tenant.

### 4. M13-owned, validated read interfaces (proposed)

New internal types live in `publishing.reads.ts`; PublishingService implements them:

1. `readRegisteredPublishingEvents({ after: {at: Date,id: UUID}|null, until: Date, limit: integer 1..200 }) -> PersistedPublishingEvent[]`. Trusted internal worker source, no public cross-tenant route. Ascending (occurredAt,id); caller receives complete registered envelope plus source row ID/position. Current normal producer timestamps are millisecond Date writes, preserving ADR-018's existing normal cursor assumption. Reject incomplete/mismatched persisted envelopes explicitly.
2. `readPublishFailures(context, {channelId,from,to,limit}) -> { items, totalCount, truncated }`. Verified tenant context, half-open [from,to), exact count and existing report caps; errors are explicit, not zero successes.
3. `scanPublishingEvents(context, {from,to,cursor?,limit}) -> { rows,nextCursor }`. OWNER diagnostic/replay source, explicit finite half-open time range, limit 1..200, opaque exact-microsecond timestamp+ID continuation bound to workspace/range. Returns persisted envelope material plus validation outcome so a poison record is reportable rather than aborting the diagnostic scan. Internal-only returned material never becomes a raw public payload. For replay provide `scanPublishingEventsTx(tx, context, range)` with the same bounded contract and row SHARE locks; it rechecks the expected page and hashes in the transaction used for M17 insertion/audit. M13 owns this query even though the transaction is supplied by M17. No M17 direct outbox-table access.

M13 owns every outbox query. M17 owns its notification receipt queries. Neither module directly queries the other's table. The scan codec is M13-owned in publishing.reads.ts, uses the same canonical microsecond timestamp rules as ADR-024, and purpose publishing-intake-scan plus workspace/from/to. It does not import an admin service or treat a cursor as authorization; no new dependency.

### 5. Operator-detectable gaps and bounded recovery

Proposed OWNER-only routes, subject to explicit Core approval:

- `GET /api/v1/workspaces/:workspaceId/notifications/intake-gaps?from=&to=&cursor=&limit=`.
- `POST /api/v1/workspaces/:workspaceId/notifications/intake-replay` with `{from,to,cursor?,limit?,dryRun,reason,expectedEvents?}`.

Dates require offsets and finite from < to; limit defaults to existing batch size 200, hard maximum 200 per call. No default history/retention interval. Reason 3..500 characters. Reject unknown/malformed fields, foreign cursor/range and unauthorized user before reads/writes. No UI addition. These routes extend the candidate file inventory and need an explicit architecture decision, not merely risk acceptance.

Diagnostic M17 service calls M13 scan and looks up its own `notification_events` by exact source key `m13:outbox:<eventId>` and workspace. Public response contains eventId/type/version, occurrence time, position relative to normal intake cursor, validation code, receipt presence/fan-out state, canonical envelope SHA-256, nextCursor and `completeForThisScan`. No raw model/media/user payload. Missing receipt is a candidate gap, not proof of accidental loss: startup history may be intentionally excluded. A receipt proves intake acceptance, not user notification or email delivery.

A finite scan can observe and report late-commit/skew gaps behind the normal cursor, stalled poison IDs and malformed envelopes. It cannot discover a row that commits after it passes that tuple. The runbook therefore requires repeat scans after the incident/quiescence window, records covered ranges/cursors, and never claims universal completeness. Clock/transaction bound or an external monitoring SLA is not invented. Metrics/logs expose source failure/last cursor and scanned gap counts without high-cardinality payload labels; collection alone is not an installed alert.

Replay defaults to dryRun=true. A dry run returns the bounded event IDs and fingerprints, missing/accepted/invalid counts and continuation. For dryRun=false require expectedEvents `{eventId,sha256}[]` matching exactly the page being applied and a reason; reauthorize OWNER and reread/revalidate inside the operation. Changed/malformed events return 409/validation error with no writes for that page. Insert only validated missing M17 events with the SAME source keys through createMany(skipDuplicates). Do not move/reset the ordinary cursor, alter old outbox payloads, set published_at, invoke publishing, generate media or call providers. Repeat same page is idempotent.

Record recovery actor/workspace, range, IDs/hashes/counts, reason and outcome through an additive M19-owned `AuditService.recordTx(tx,entry)` seam in the same transaction as notification event inserts. Failure rolls back replay; M17 does not write the audit table directly. No raw payload in audit. After commit, ordinary fan-out may notify under existing preferences; no immediate fake/email SENT result is returned.

Bounded runbook: (a) identify tenant/source and incident range explicitly, inspect current cursor and errors; (b) page diagnostics/dry run, record fingerprints and incomplete scans; (c) obtain operator approval for target scope, repair malformed producer data only through a reviewed correction procedure, never arbitrary delete/skip; (d) replay approved valid pages with expected hashes; (e) repeat dry run to check dedupe and rescan after late transactions settle; (f) separately inspect fan-out/delivery. A poisoned normal page remains blocked until a reviewed producer/data correction makes it valid. No unsafe live-cursor leap is provided by this recovery endpoint. Old invalid rows can require a separate reviewed corrective migration/procedure; accepted risk remains visible.

### 6. Publishing correlation persistence and legacy behavior

Add nullable `originCorrelationId: UUID` and `correlationOrigin: REQUEST | WORKFLOW | LEGACY_RECOVERY` to PublishJob and PublishAttempt, with consistency CHECKs. M16 passes its run correlation through an optional internal command option. HTTP publishing controller passes validated current request correlation. On first attempt claim persist origin on job and copy to attempt BEFORE platform execution; retries/reconcile reuse it. Do not use schedule-creation correlation as though it were a later publish trigger. Concurrent claims preserve the existing winner.

Legacy job/attempt rows stay null on migration; no random backfill of a supposed origin. When a still-active legacy attempt is next processed, atomically persist a stable recovery UUID derived from a documented namespace `reelforge:legacy-publish:v1` plus workspace/job identity; mark LEGACY_RECOVERY. Events then carry a valid stable correlation but history/runbook explicitly says the original origin is unknown. Existing outbox events are unchanged; no v1 wire provenance field is invented. Recovery correlation is not proof of original trace continuity.

### 7. Every final failure, transactionality and dedupe

M13 owns a transaction-scoped event builder used by verified success/rejection and markAttemptFailure, including upload-initiation rejection/session-persist exhaustion branches that actually terminalize a persisted attempt. Failure event and attempt/job/destination final state commit together or roll back together. Preflight denials with no persisted final attempt are not fabricated publishing events. Uncertain upload outcomes stay RECONCILIATION_REQUIRED; never force them to FAILED_FINAL just for notification coverage.

New failure identity is `publish-failed:<destinationId>:attempt:<attemptNumber>`, unique per workspace via existing outbox key. Same-attempt concurrent finalization/reconcile uses CAS/upsert and preserves first eventId, occurredAt and correlation. A later genuinely distinct attempt may emit its own failure. Successful publication retains current `post-published:<destinationId>` identity.

Already-final legacy rows are not automatically backfilled. Do not regenerate an existing `publish-failed:<destinationId>` legacy event under the new key. If historical data has inconsistent legacy event/final-state combinations, report ambiguity for reviewed recovery rather than guessing which attempt it represents. New transitions of still-active legacy attempts use new attempt identity and marked recovery correlation. No historical failure-count completeness claim is made.

### 8. Publication safety versus notification safety

Publishing remains protected by its authorization, quality, rights, preflight, persisted upload attempt/session and uncertain-outcome reconciliation. Missing notification receipt does NOT authorize another upload; replay never calls publishNow/retry/reconcile. Conversely, a successful outbox/receipt transaction does not establish remote publication or email delivery. Reports count persisted final-failure events with exact bounded read semantics and limitations; they do not infer a remote failure from a missing notification.

### 9. Failure/recovery matrix

| Failure                                   | Expected result                              | Recovery/guarantee limit                                                       |
| ----------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------ |
| Late commit/skew behind watermark         | Normal intake may miss row                   | Explicit diagnostic+replay may repair observed row; repeat finite scans needed |
| Fresh source/no-history                   | Old rows excluded intentionally              | Explicit bounded owner replay, not automatic backfill                          |
| Invalid/unknown event at page head        | No cursor advance/page insert; visible error | Retry same page; reviewed repair, no silent skip/DLQ                           |
| Crash/read failure before intake commit   | No page advancement                          | Next tick retries; dedupe unchanged                                            |
| Crash after receipt/cursor commit         | Receipt durable                              | Normal replay/reset cannot duplicate source key                                |
| Fan-out or email fails                    | Intake receipt may still exist               | Inspect distinct fan-out/delivery state; no delivered claim                    |
| Diagnostic page raced by late transaction | Scan may omit later commit                   | Repeat range scan; no eventual-delivery assertion                              |
| Recovery expected hash mismatch           | 409 and no page writes                       | Inspect fresh dry run; no arbitrary changed input replay                       |
| Replay/audit DB write fails               | Both roll back                               | Same approved page can retry safely                                            |
| Publishing event insert fails             | Final-state transaction rolls back           | Existing publishing reconciliation; no second upload permission                |
| Legacy unknown origin                     | Persist LEGACY_RECOVERY on active processing | Original trace remains unknown                                                 |
