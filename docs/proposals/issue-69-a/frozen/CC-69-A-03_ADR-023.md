#### S1: channel active-snapshot FK

Current DB: `channels_active_snapshot_fkey`: `(workspace_id,active_snapshot_id)` -> `channel_config_snapshots(workspace_id,id)`, DELETE SET NULL, UPDATE CASCADE. Schema expects `channels_workspace_id_active_snapshot_id_fkey`, DELETE RESTRICT, UPDATE CASCADE.

SET NULL has no column list, so it attempts to null workspace_id as well as the optional pointer; workspace_id is NOT NULL. This does not implement a safe pointer clear. Recommendation: RESTRICT, preserving ADR-015 immutable snapshot references and tenant identity. Alternative: SET NULL(active_snapshot_id) requires a different approved pointer-deletion policy and representability review; not selected implicitly. Snapshot deletion is not an existing user workflow to expand here.

Row-preserving DDL strategy, subject to exact SQL review: lock/transactionally add the intended FK NOT VALID, validate existing references, then remove the old FK with all changes committed together. No unprotected interval exposed to application writes, no tenant key nulling, no delete/backfill. If invalid data or locks prevent safe validation, abort/rollback and report; do not fix by deleting rows. Different SQLSTATE/error behavior on active-snapshot deletion is an intentional compatibility impact to test.

## Revision 2 — ADR-021 C1 accounting/schema dependency

**PENDING renewed Core decision on these dependent details.** Minu #6832033899 accepts S1–S5 direction and preservation requirements, subject to separate exact SQL review. That acceptance is not revoked or expanded by this amendment. No migration is created or applied.

The complete revised ADR-021 revision 2 is normative for the new operation model: READY must reference an M18 RESERVED hold and ProviderRequest FAILED/NOT_DISPATCHED/dispatched:false with NULL actualCost. Expiry then yields zero spend even with no recovery invocation. T2 atomically commits DISPATCHING plus ledger FAILED/PENDING/dispatched:true before invocation; no pre-dispatch recovery may reverse it. UNCERTAIN remains estimate-covered through live hold or expired-hold ledger fallback; terminal committed holds exclude matching ledger. No new PRE_DISPATCH_ERROR_CODES literal is proposed; post-dispatch classifications must never enter that allowlist.

No extra expiry field is needed: the linked reservation.expiresAt is authoritative. Existing proposed dispatchStartedAt and dispatchDeadlineAt are required for the claim/diagnostic distinction. Operation SQL CHECKs must enforce READY/NOT_DISPATCHED having NULL dispatchStartedAt/deadline, and DISPATCHING/UNCERTAIN/RESULT_READY/FAILED/SUCCEEDED having non-null dispatchStartedAt/deadline. READY has required reservation/request links, NULL domain result and completion fields; NOT_DISPATCHED has a completion timestamp. Keep the proposed single attemptNumber=1 and tenant/link consistency constraints.

Cross-table state/ledger/hold equality cannot be expressed as an ordinary PostgreSQL CHECK. Do not pretend those row CHECKs prove it. M08/M18 owning transaction methods provide the atomic invariant, and the specified database interleaving tests must verify it with the real existing classifier. Direct administrative SQL modification remains outside that guarantee. T1 uses a transaction-scoped advisory identity lock, creates hold/ledger before inserting the fully linked READY operation, and commits all together; no half-linked committed or transient READY row is needed, and no new deferrable-FK/triggers are assumed.

Recovery transitions READY to terminal NOT_DISPATCHED by locked recheck and releases only a provably unused live hold. It never deletes a row, allocates a replacement attempt, resets accounting dates or releases a DISPATCHING/UNCERTAIN hold. The READY recovery candidate scan uses the already proposed workspace/state/created_at index and linked hold lookup; no new retention policy or automatic data purge. All row-preserving S1–S5 recommendations and existing SQL-only protection requirements remain unchanged.

Additional required empirical tests (NOT RUN): abandoned READY/no T2/no sweep with day/month expiry produces zero spend; recovery closure is idempotent; T2 versus recovery/expiry lock interleavings never revert a dispatched marker; changed periods never reopen a key; T3 rollback plus hold expiry retains uncertain liability without double count; ambiguous T2 commit acknowledgement never triggers a provider invocation. Snapshot prior data/migration checksums and SQL-only objects before/after as already required. Exact future SQL remains separately review-gated, and Manager must still release Gate 0 after independent architecture decisions.
