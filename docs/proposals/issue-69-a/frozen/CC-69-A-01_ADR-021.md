# CC-69-A-01 / proposed ADR-021 — M08 paid AI operation boundary

**Status: PENDING. No architectural or implementation approval.**

## CHANGE_CONTROL proposal

- **Change ID/class:** CC-69-A-01; security/reliability correctness and cross-module extraction, not provider implementation.
- **Problem/evidence:** At base `1892653`, M06 `IdeaService.propose`, M11 `QualityService.create` and M15 `PerformanceIntelligenceService` invoke their AI ports without M08 ledger/M18 authorization. M06 validates some channel/series ownership only after the call. Existing M07/M09 accounting is embedded in their services; M18 `reservePaidCall` calls its own transaction, returns null for missing policy and `finishPaidCall` catches settlement failures. Those APIs cannot simply be nested inside a new transaction and called atomic.
- **Proposed behavior:** Establish M08-owned PaidAiModule for these three paths; validate before dispatch; persist one operation/attempt; atomically reserve/account; never replay an uncertain paid invocation. Detailed specification below.
- **User/business value:** Prevent unauthorized/unbudgeted calls, duplicate charges and hidden failed-call spend while retaining honest unavailable/manual-review behavior.
- **Affected modules/APIs/schema/events/prompts/pipelines:** M06/M08/M11/M15/M18, M16 quality consumer and M19 stop. New operation model, narrow provider-port metadata and paid-operation key; existing provider_requests and usage_reservations remain financial sources. No publishing event payload, creative prompt policy or vendor binding changes.
- **Cost/security/privacy/policy/reliability impact:** New DB transactions and tenant-owned operation records. Stored normalized provider output can contain user content; no credential/raw transport dump. No new retention duration; existing owner retention decision remains open. Estimates reserve conservatively using existing money rounding; provider overshoot cannot be retroactively prevented. No paid call from tests/startup/health.
- **Backward compatibility/migration:** M07 manual missing-M18 behavior and M09 execution remain unchanged. Defaults remain unavailable. New configured paid HTTP paths require stable keys; existing M11 unconfigured manual review and M15 deterministic reports remain usable. Additive model only after ADR-023 approval; no historical operation backfill.
- **Acceptance criteria/tests:** T21-01..12 below, all planned/unexecuted.
- **Trade-offs/deferred:** A supports one dispatch attempt per operation, no automatic paid retry, no live reconciliation/provider lookup, no async video adapter, no M07/M09 broad refactor, no vendor choice. Uncertain operations can require manual authorized reconciliation.
- **Owner decision:** A-POL-01 recorded in [#6831450311](https://github.com/imTusharsingh/reelforge/issues/69#issuecomment-6831450311): fail closed on unavailable/unconfigured M18 for new M06/M11/M15 paths; M07 unchanged. Other numerical/interface/schema choices below are proposals, not owner-approved values.
- **Core Reviewer decision:** PENDING. [#6831527297](https://github.com/imTusharsingh/reelforge/issues/69#issuecomment-6831527297) accepts policy direction only and specifically requires atomicity, stable attempt identity, overspend/timeout/uncertainty and PostgreSQL tests.

## ADR-021 proposed decision

### 1. Alternatives and recommendation

1. Put shared logic in ScriptModule: reject, because M06/M11/M15 then depend on M07 ownership.
2. Duplicate ledger/reservation code: reject, because crash/dispatch semantics drift.
3. M08-owned PaidAiModule: **recommend**. Reuse ProviderRegistry, CapabilityMetadata/ProviderProvenance and M18 money/budget logic. M18 never executes the provider. The new module is an accounting boundary, not a generic vendor framework.

### 2. Ownership and dependencies

PaidAiModule imports IdentityModule for DATABASE, UsageBudgetModule and EmergencyStopModule. M06/M11/M15 modules import PaidAiModule; no reverse domain dependency. M08 owns operation state and provider_requests writes. M18 alone owns budget locks, limit evaluation, reservation status/amounts and usage accounting. Core owns the Prisma schema and exported port modifications. Domain consumers own input validation, normalized result validation and their table writes.

M08 does not write usage_reservations directly. M18 does not select a provider or write generated ideas/reviews/reports. No transaction callback can perform network/storage side effects.

### 3. Exact proposed interfaces and identity

Specification types (not existing symbols):

- `PaidAiKind = IDEA_PROPOSAL | QUALITY_REVIEW | INSIGHT_NARRATIVE`.
- `PaidAiCommand`: verified workspace context; canonical nullable channelId; kind; UUID operationKey; UUID originCorrelationId; optional verified workflowRunId; registered capability; immutable provider-configuration identity; versioned normalized request; validated server-derived estimate; dispatchTimeoutMs.
- `execute(command, adapter) -> Promise<{ operationId, attemptId, resultRef }>`.
- Adapter seam: `invoke({ attemptId, originCorrelationId, signal })`, `validate(response) -> { normalizedResult, provenance }`, `persist(tx, normalizedResult) -> { resultType, resultId }`. `signal` is cancellation advice only, not proof of non-dispatch. `persist` is DB-only and runs under the operation lock.
- `readOperation(context, operationKey, kind)` is an internal scoped read returning state, safe reason and domain reference; domain services reauthorize before returning a replay result. No new public operator/vendor reconciliation endpoint is included.

For HTTP, propose `Idempotency-Key: <UUID>` on configured paid M06/M11/M15 actions. For M16 quality calls use the persisted step idempotency identity mapped deterministically to a UUID in the namespace `reelforge:paid-ai:v1`; retain the workflow trace correlation separately. HTTP transport retries retain their original key. A missing key is 400 only when a paid dispatch is otherwise configured/eligible. Defaults remain: M06/M07 503 NOT_CONFIGURED; M11 null-scorecard manual review; M15 explicit deterministic-only report. No fake AI result.

New `PaidAiOperation` model, database name `paid_ai_operations`:

| Field                                              | Proposed type/constraint                                                                                                                      |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| id, workspaceId                                    | UUID; primary key id, compound unique(workspaceId,id); workspace FK CASCADE                                                                   |
| kind, operationKey                                 | enum above and UUID; unique(workspaceId,kind,operationKey)                                                                                    |
| attemptId, attemptNumber                           | UUID unique; integer fixed at 1 by CHECK in A                                                                                                 |
| channelId, workflowRunId                           | nullable UUID; tenant-compound NO ACTION references when present (ADR-023)                                                                    |
| originCorrelationId                                | required UUID; trace provenance, not dedup identity                                                                                           |

| providerId, capabilityId, providerConfigurationId  | required nonempty strings; never credentials                                                                                                  |
| estimate, currency                                 | Decimal(18,8) nonnegative and uppercase three-letter currency                                                                                 |
| budgetAuthorization                                | immutable JSON containing applicable budget IDs, versions and period boundaries captured by M18                                               |

| normalizedResult, resultProvenance                 | nullable validated JSON; never arbitrary raw provider transport or secrets                                                                    |

An admitted row is not committed in a half-linked state. Required links and state consistency use SQL CHECKs plus tenant FKs. Existing financial rows remain authoritative; normalizedResult/estimate copies do not become an additional spend source. Operation deletion is not a retry mechanism. No automatic operation expiry/deletion/retention value is introduced.

Fingerprint version 1 is SHA-256 over canonical JSON containing kind, tenant/channel, immutable inputs and revisions, full normalized model input, provider/capability/configuration identity and estimate. Recursively sort object keys, preserve array order, reject non-finite/unsupported values. Exclude credentials, trace IDs, operation key and request time. Same key/different fingerprint is 409 PAID_OPERATION_CONFLICT. Changing providers under the same key is not a fallback.

One operation has exactly one attempt in A. Its attemptId is allocated once and is the UUID stored in ProviderRequest.correlationId and UsageReservation.correlationId; M18 reservation key remains `m08:<attemptId>`. Origin tracing is stored separately. Same-operation retries cannot allocate a new attempt number. A deliberate new generation needs a new caller operation identity, authorization and budget; a lost-response retry is not deliberate regeneration. Durable multi-attempt/provider-idempotency support belongs to a separately reviewed extension under #65.

Port changes: add readonly `capability: CapabilityMetadata` to IdeaProposalLlmPort and QualityReviewPort; add correlationId to idea invocation and insight narrative input; retain existing QualityReviewRequest.correlationId and provenance types. No cost/vendor/model IDs are invented. Registered request-priced capability amounts may be used directly; other units require an approved bounded estimator or fail COST_UNKNOWN. Estimate conversion reuses M18's existing ceil-to-minor-unit semantics.

### 4. Transaction boundaries and accounting

Propose internal M18 methods `reservePaidOperationTx(tx,input)`, `authorizePaidOperationTx(tx,hold,authorization)` and `finishPaidOperationTx(tx,hold,outcome)`. All use the caller's Prisma transaction, never start nested transactions, never swallow errors, never invoke external code. Existing public reserve/commit/release APIs preserve behavior; share their private arithmetic/validation rather than forking policy.

**T1 admission:** validate role and pinned domain prerequisites before entering. Insert/claim the operation under its unique key. M18 locks applicable budgets using its existing deterministic ordering, rereads limits, expires eligible holds, validates currency and consumed amounts, and refuses missing policy. Create the M18 hold BEFORE the ledger row; then create ProviderRequest as FAILED/NOT_DISPATCHED with dispatched:false and the estimate, link it and the hold, and commit operation READY in this same transaction. Any exception rolls back all three. No PREPARING orphan is committed. A unique race rolls back and reads the winning operation; it cannot call the provider.

**T2 dispatch claim:** lock operation, then M18 applicable budgets in the same ordering, then its reservation. Only READY may proceed. Recheck membership/stop, hold RESERVED/not expired, budget IDs/versions/currency/period authorization and current limits including this hold exactly once. A changed period/budget set/version or expired hold refuses dispatch and atomically marks NOT_DISPATCHED/releases the unused hold. Commit a pre-dispatch refusal/release as a transaction result, then translate it to an HTTP exception outside the transaction; throwing inside the transaction must not accidentally roll back that safe terminalization. Do not renew or mutate old period accounting silently. Set ProviderRequest FAILED/PENDING with dispatched:true and operation DISPATCHING/deadline; commit before invocation. This commit is the conservative dispatch boundary: a crash immediately afterwards is ambiguous, never proof that nothing was sent.

Stop ordering follows ADR-019: no new dispatch after a preflight observes a stop. A stop arriving after the durable dispatch claim does not retroactively cancel an authorized in-flight call. GLOBAL environment updates have no cross-process transactional guarantee; that limitation is not represented as linearizable global cancellation.

**Invocation:** outside all transactions and budget locks, once. Proposed default deadline 120,000 ms, allowed configured range 1..300,000 ms for these synchronous AI paths. These numbers are PENDING Core choices, not approved operational values. Reuse existing 60-minute M18 paid hold lifetime; it is an accounting hold, not a retention policy. Deadline abort is not evidence that the provider stopped or did not bill. No automatic provider retry.

**T3 financial/result settlement:** lock operation, budgets, reservation in that order. For a validated successful response, atomically store normalizedResult/provenance, terminal ledger actual/unknown cost, M18 commitment actual-or-estimate and operation RESULT_READY. For a definitively unusable completed response, persist FAILED, ledger FAILED with dispatched:true/actualCost:null and commit the estimate. For timeout/disconnect/crash ambiguity, persist UNCERTAIN and the failed-estimated ledger liability but leave the hold RESERVED until valid outcome settlement or expiry; the live hold counts the estimate, then the ledger counts it after expiry. This is conservative budget charging, not a claim of a known provider bill. An uncertain operation is never released merely because its hold expired. This distinction permits a late validated response to commit the original RESERVED/EXPIRED hold exactly once using existing M18 semantics; do not attempt to overwrite an already COMMITTED amount. Never take a raw provider error code as proof of non-dispatch. If T3 fails, it rolls back; DISPATCHING/PENDING plus the hold remain. When the hold expires, the ledger estimate counts again under existing M18 exclusion rules. Failure cannot create a zero-charge gap.

**T4 domain persistence:** lock RESULT_READY, invoke the DB-only domain persistence callback and set result reference/SUCCEEDED in the same transaction. Failure leaves RESULT_READY and already-accounted validated output for safe persistence retry. No second provider call. Same-key success returns the stored domain reference after reauthorization, not the provider callback.

M08 ledger and M18 reservation never count twice: existing live/committed reservation exclusion joins by workspace+attemptId; expired holds fall back to the ledger. Budget preflight sees the hold before it sees this call's ledger in T1. New origin/workflow linkage in M18 ledger reads uses the operation record for these new calls without changing M07 joins. Default/manual legacy paths do not migrate automatically.

Admission prevents concurrent estimated commitments exceeding a limit. It cannot prevent a provider charging more than a valid estimate. A real adapter must preflight a defensible upper bound; a reported overrun is recorded at actual cost, flagged ESTIMATE_OVERRUN and blocks subsequent admissions as applicable. Never discard actual cost to keep a budget artificially green. No FX is added.

### 5. Reconciliation and compatibility

Timeout/disconnect/caller cancellation/worker death after T2 => UNCERTAIN or a DISPATCHING record whose deadline has elapsed; no replayed invocation. An operator can inspect this through existing operational diagnostics/logging plus the internal read contract; the ledger remains conservatively chargeable. A deadline detector may mark UNCERTAIN by CAS, never release a dispatched hold. A late successful response may settle a still-matching DISPATCHING/UNCERTAIN attempt and original RESERVED/EXPIRED hold idempotently. If the hold is already COMMITTED at an estimate for a definitive terminal failure, do not mutate it to a different amount: flag conflicting evidence for existing OWNER-audited correction, never an automatic adjustment or redispatch. Terminal SUCCESS/FAILED cannot be overwritten silently.

If valid output was durably stored, replay performs only T4. If provider output was lost, A does not invent it or query a live provider automatically. Record the blocked operation, use separately owner-authorized evidence lookup under #65 if available, and use existing audited adjustments for verified financial corrections. A credit is not permission to redispatch. No 'force retry' endpoint or automatic new attempt is included.

M07 missing-M18-budget policy is explicitly unchanged by owner A-POL-01. Tightening it would need another owner policy decision and Core review. C2's typed unavailable correction is separate. Existing M11/M15 provider-NOT_CONFIGURED behavior retains honest AI-unavailable/deterministic-only limitations. For a configured paid path, M18 absence, budget refusal and trusted stop are propagated as typed authorization failures (503 BUDGET_POLICY_UNAVAILABLE, 409 budget/stop); broad optional-provider catches must not swallow them. An actual dispatched provider failure may still use the existing explicit manual-review/deterministic-only fallback after its paid liability is recorded, never an AI score/narrative fabrication. A failure fallback is not a second provider attempt. API error distinctions: 400 invalid key/input; 403 role/tenant membership; scoped 404 resource; 409 operation conflict/in-progress/uncertain, budget exhaustion/currency/stop; 503 NOT_CONFIGURED or infrastructure admission failure. Default unconfigured M06/M07 use code NOT_CONFIGURED, not raw registry errors.

## Revision 2 — mandatory pre-dispatch accounting amendment

**PENDING renewed Core decision.** Responds to Minu #6832033899, HIGH C1. This section overrides any ambiguous T1/T2/recovery wording above. ADR-022/024 were accepted at their original posted versions; ADR-023 was directionally accepted subject to separate SQL review and this repair. Neither this revision nor those decisions release Gate 0.

### Exact state/ledger invariant

ProviderRequest is created in T1, in the SAME transaction as operation READY and M18 RESERVED. Its exact status is FAILED, errorCode is literal NOT_DISPATCHED, actualCost is NULL, estimatedCost retains the estimate, and responseMetadata.dispatched is false. NOT_DISPATCHED is already in current PRE_DISPATCH_ERROR_CODES; no new allowlist value is necessary. READY must NEVER use PENDING or any other errorCode. Failed admission rolls back operation, hold and ledger together.

| Operation state | ProviderRequest.status | Exact errorCode        | dispatched | Budget classification                                                                     |
| --------------- | ---------------------- | ---------------------- | ---------- | ----------------------------------------------------------------------------------------- |
| READY           | FAILED                 | NOT_DISPATCHED         | false      | Live RESERVED hold counts estimate; after expiry ledger is NOT_DISPATCHED and counts zero |
| NOT_DISPATCHED  | FAILED                 | NOT_DISPATCHED         | false      | Released/expired hold and ledger count zero; no actual cost                               |
| DISPATCHING     | FAILED                 | PENDING                | true       | Live hold counts estimate; after expiry ledger counts ESTIMATED                           |
| UNCERTAIN       | FAILED                 | PAID_OUTCOME_UNCERTAIN | true       | Live hold counts estimate; after expiry ledger counts FAILED_ESTIMATED                    |
| RESULT_READY    | SUCCEEDED              | NULL                   | true       | COMMITTED actual-or-estimate hold counts; matching ledger excluded                        |
| SUCCEEDED       | SUCCEEDED              | NULL                   | true       | Same settled accounting as RESULT_READY; domain result durable                            |
| FAILED          | FAILED                 | PAID_DISPATCH_FAILED   | true       | COMMITTED estimate counts; matching ledger excluded                                       |

The new PAID_OUTCOME_UNCERTAIN and PAID_DISPATCH_FAILED literals MUST NOT be added to PRE_DISPATCH_ERROR_CODES. Never copy provider error codes into this classification field; retain only separately sanitized diagnostics. Actual-cost fields in RESULT_READY/SUCCEEDED are validated amount or NULL; failed/uncertain states retain NULL actual and conservative estimate. A non-null actual cost must never be attached to READY/NOT_DISPATCHED because current classifyCost gives actual cost precedence over errorCode.

For every row, committed holds exclude the matching ledger; unexpired RESERVED holds exclude it and count the reserved estimate; expired holds no longer exclude it. Therefore expiry cannot create false spend for READY, and cannot erase liability for DISPATCHING/UNCERTAIN. A COMMITTED hold for READY/NOT_DISPATCHED is forbidden. Expiry does not prove provider cancellation or free failure. Invocation deadline bounds remain proposed waiting limits only.

### Atomic claim, recovery and lock ordering

All M08 transitions lock in this order: operation row, applicable budget rows in existing M18 deterministic order, its reservation row, its provider-request row. No network action occurs under locks. T1 takes a transaction-scoped advisory identity lock derived from workspace/kind/operationKey before budget locks, and locks any existing operation row. Hash collisions only serialize unrelated admissions; the full unique key remains authoritative. For a new identity it allocates identifiers, creates the hold and exact non-dispatched ledger, then inserts READY with complete links before committing. Thus immediate state/link CHECKs never require a half-linked READY insert. No provider is called inside this transaction; any uniqueness failure rolls back all new rows and reads the winner. Generic existing M18 expiry may lock budget/reservation rows, but must never acquire an operation lock afterwards or rewrite operation/ledger state. This is one-way lock ordering, not a nested transaction.

T2 obtains locks, reads database time AFTER lock acquisition, rereads operation READY plus dispatchStartedAt IS NULL, hold RESERVED, expiresAt > current database time, and budget IDs/versions/period authorization. Reread stop/authorization as already specified. On success it atomically changes operation to DISPATCHING with dispatchStartedAt/deadline AND changes the ledger to FAILED/PENDING/dispatched:true. Commit BOTH before invoking once. If commit acknowledgement is ambiguous, DO NOT invoke: query the durable state for diagnosis, mark/retain uncertainty if claimed, and never infer permission to send from a lost acknowledgement. A crash in this gap may conservatively charge a call never actually sent; it is an uncertain durable dispatch claim, distinct from provably unclaimed READY.

A changed budget period, budget version/set, stop, expired hold or other failed pre-dispatch authorization results in one transaction committing operation NOT_DISPATCHED, ledger FAILED/NOT_DISPATCHED/dispatched:false/actualCost NULL, and release of a still-live unused hold. An already EXPIRED hold stays expired. Translate refusal to an exception AFTER transaction commit. Never throw inside that transaction and accidentally undo safe closure. No automatic re-reservation, attempt increment or new-period dispatch under the old key.

Add internal `PaidAiService.recoverReady({workspaceId?,limit,now?})`: bounded scan of READY rows whose linked hold has expired or is already EXPIRED/RELEASED, then row-lock/recheck each candidate with the SAME ordering. Database time, not a caller-supplied production time, is authoritative (now override is a test seam only). Lock may use SKIP LOCKED; a skipped row remains observable for the next pass. If still READY/unclaimed, close NOT_DISPATCHED and preserve the exact zero-charge ledger invariant; release if necessary through M18. If DISPATCHING/UNCERTAIN/RESULT_READY/terminal, recovery performs NO pre-dispatch rewrite or release. No row deletion and no provider invocation.

Schedule this bounded bookkeeping recovery on the existing worker orchestration tick via an M08-owned service method, before dispatch work, and expose counts/errors through existing redacted worker diagnostics. Limit defaults to existing batch bound 200; no new retention period or paid retry policy. Failure reports error and leaves data for the next tick. Even if no sweep EVER runs after a crash, an abandoned READY's expired hold and NOT_DISPATCHED ledger count zero. The sweep is for terminalization/visibility, not a prerequisite for correct spend.

Same-key replay: SUCCEEDED returns authorized stored reference; RESULT_READY may retry DB-only persistence; READY performs NO second admission/invocation on the replay request and returns 409 PAID_OPERATION_IN_PROGRESS until the original claimant proceeds or recovery closes it. Expired READY can be safely closed on that read using the recovery transaction. NOT_DISPATCHED is a terminal same-key result/refusal, not permission to dispatch. DISPATCHING/UNCERTAIN returns 409 requiring reconciliation. Changed fingerprint is always 409, including a changed selected provider or estimate. A new budget period does not reopen an old key. Deliberate new work requires a separately authorized new operation key; M07 remains unchanged.

T2 versus recoverReady: operation lock serializes them. If T2 wins before expiry, recovery sees DISPATCHING and cannot reverse the chargeable marker. If recovery wins after expiry, T2 sees NOT_DISPATCHED and cannot invoke. If T2 waits across expiry/day/month boundary, post-lock checks refuse and close safely. Generic M18 expiry can only expire the hold; T2 must fail its locked recheck if expiry wins. It cannot rewrite a dispatched ledger to NOT_DISPATCHED. T3 settlement locks the same rows; failure rolls back financial/result changes and leaves the already-chargeable T2 marker. For a timed-out UNCERTAIN operation leave the hold uncommitted until outcome/expiry; late validated results can commit RESERVED/EXPIRED once. Existing irreversible COMMITTED amounts require owner-audited correction if conflicting later evidence appears, never an unreviewed overwrite.
